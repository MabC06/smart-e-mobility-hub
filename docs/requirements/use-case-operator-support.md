> **Status:** Draft v1.1 · **Owner:** M7 (Nguyễn Trung Kiên) · **Date:** 2026-10-15 · **Reviewer:** M5 (Đỗ Hoàng Việt)
> This document specifies the operator-side use cases across the system to support M2 in building the overview use-case diagram (Phase 1) and laying the groundwork for the Phase 1 Operator Dashboard wireframes.
> Terminology, actor names, objective IDs (`O-x`), and assumptions (`A-xx`, `D-xxx`) follow `docs/report/01-introduction.md` and `docs/design/architecture/tech-stack-proposal.md`.
> Most operator screens are UI views of use cases owned by other modules (CONTRIBUTING section 5, `D-011`). IDs of other modules are quoted as in their current files; `UC-M4-0x` assumes M4 renumbers `UC-A0x` (`D-012` already cites `UC-M4-07`), and M6's former UC-12 is now UC-M6-01.
> The `Related FR / Obj` column carries the FR part of `Trace:`; BRs are added as `BR-M<n>-##` where the owner's IDs are final.

## 1. Operator Actor Profile & Scope Alignment

In accordance with Section 1.4 and Section 1.7 of `docs/report/01-introduction.md`, the **Operator** is a primary human actor interacting directly with the system through the screen-based **Operator Dashboard**.

| Attribute | Specification |
|---|---|
| **Actor Name** | `Operator` |
| **Role Type** | Primary actor (human user authenticated via seeded operator account per `A-06`) |
| **Core Responsibilities** | Monitor real-time network health across all Mobility Hubs (`FR-01`, `FR-08`), handle operational incidents and equipment failures (`FR-09`), coordinate rental vehicle redistribution (`FR-10`), oversee and adjust smart charging priorities/schedules (`FR-11`), and run isolated What-if Simulation scenarios to evaluate coordination recommendations (`FR-12`). |
| **Related System Objectives** | `O-1` (real-time resource visibility), `O-3` (charging efficiency), `O-4` (capacity alerts, incident resolution, vehicle redistribution), `O-5` (What-if simulation & coordination planning). |
| **Interacting Secondary Actors** | `Sensor / event source` (simulated by `iot_sim` per `D-004`, which feeds battery levels, parking occupancy, charging-point failures, and demand events into `core`). |

## 4. UI / UX Implications for Phase 1 Wireframes (M7 Preview)

To ensure seamless traceability from Phase 0 requirements to Phase 1 UI design (`docs/design/ui/wireframes-operator.md`), the Operator Dashboard will be structured around four primary views corresponding directly to the use cases above:

1. **Network & Hub Overview Screen (`UC-M7-01`, `UC-M7-02`, `UC-M7-07`):** Summary cards for all 10 Hubs, real-time occupancy/charging bars, active capacity alert ticker, and drill-down resource state controls.
2. **Dispatch & Charging Coordination Screen (`UC-M7-03`, `UC-M7-04`, `UC-M7-05`, `UC-M7-06`):** Split view showing charging priority queues per Hub and the vehicle redistribution dispatch builder.
3. **Incident Management Screen (`UC-M7-08`):** Filterable incident table (by severity, status, Hub, resource type), escalation status badge, and resolution modal linked to resource state transitions.
4. **What-if Simulation Lab Screen (`UC-M7-09`, `UC-M7-10`):** Scenario selector (5 standard scenarios), configurable parameter form, isolated snapshot banner, impact metrics comparison chart, and recommendation cards.
