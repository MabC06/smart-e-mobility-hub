## 1. Project Overview

Smart E-Mobility Hub is a coordination system for shared electric mobility resources (e-bikes/e-scooters) across the VNU-HCM Urban Area. It manages Mobility Hubs consisting of parking spaces, charging points, and vehicles, serving two main actor groups: students (rent vehicles, reserve, charge) and operators (monitor, handle incidents, coordinate, run What-if Simulations).

The final report is graded on the full SE process: Requirements → Architecture → Structural/Behavioral Design → UI Design → What-if Simulation Design → Implementation → Testing → Evaluation, plus an AI Usage Declaration and a presentation + 3-minute demo video.

No hardware is used — vehicle, parking and charging-point state comes from simulated data generated by the IoT simulator (owned by M8, see below).

**Notes:**

- The Design phase (Phase 1) is the bottleneck — the Oct 26 design-review milestone should be treated as fixed and non-negotiable.
- M1 is a dependency for the whole team in Sprint 1 — prioritize getting a minimal working version of the core domain out within the first few days (Oct 27–30), even before all diagrams are polished.
- M8 owns the IoT simulator, which feeds simulated data into `core` for everyone else to build against — like M1, it should aim to have a minimal working version ready early in Sprint 1, not just at the end.
- M7 and M8 aren't tied to a single FR, so they risk being under-utilized early on — assign them supporting work on other modules (secondary diagrams, sample test data) during Phases 0–1.
- The Testing phase (Phase 4) is tight — test cases should be written alongside code during Sprint 2, not left entirely until Phase 4.
- Code freeze (Nov 13) means no new features or interface changes. Bugs found during testing can still be fixed until Nov 19, through the normal PR process.
- Write each report section right after its diagrams are done (Phase 1) and revise it in Phase 3, so Phase 5 is only for finishing and assembling, not for writing from scratch.
- Nov 23 is the internal report freeze; Nov 24–25 is buffer, because the official deadline has not been announced and may be earlier than Nov 25.
- Until the minimal `core` lands on Oct 30, M2–M6 should code against stubs/mocks that follow the Core API spec (v1, Oct 20) instead of waiting.
